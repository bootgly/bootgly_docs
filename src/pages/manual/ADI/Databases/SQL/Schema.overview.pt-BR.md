# Schema Builder

O Schema Builder é **como você molda seu banco**. Você o chama de dentro de uma migration para
criar, alterar ou remover tabelas e índices — nunca SQL raw — e ele escreve o SQL que a sua engine
(PostgreSQL, MySQL ou SQLite) espera.

Todo método só **compila**: retorna uma `Query` — o texto da instrução e seus parâmetros — e não
toca em banco nenhum. O Runner de migrations roda o que uma migration retorna; fora de uma
migration, você mesmo entrega a query ao `$Database->query()`.

> Novo aqui? Siga primeiro o guia
> **[Database migrations](/guide/database-migrations/overview/)** — ele mostra o fluxo
> inteiro. Esta página é o que você faz dentro do `Up`/`Down`.

## As cinco coisas que você vai fazer

Dentro de uma migration você recebe um `$Schema`. Com ele você quase sempre faz uma destas:

```php
use Bootgly\ADI\Databases\SQL\Builder\Expression;
use Bootgly\ADI\Databases\SQL\Schema\Auxiliaries\Keys;
use Bootgly\ADI\Databases\SQL\Schema\Auxiliaries\Types;
use Bootgly\ADI\Databases\SQL\Schema\Blueprint;

// 1. Create a table
$Schema->create('users', function (Blueprint $Table): void {
   $Table->add('id', Types::BigInteger)->generate()->constrain(Keys::Primary);
   $Table->add('email', Types::String)->limit(190)->constrain(Keys::Unique);
   $Table->add('active', Types::Boolean)->default = true;
   $Table->add('created_at', Types::Timestamp)->default = new Expression('CURRENT_TIMESTAMP');
});

// 2. Change it
$Schema->alter('users', function (Blueprint $Table): void {
   $Table->add('bio', Types::Text)->nullable = true;  // a new nullable column
});

// 3. Index a column
$Schema->index('users', 'created_at');               // users_created_at_index

// 4. Rename it
$Schema->rename('users', 'members');

// 5. Drop it
$Schema->drop('members');
```

Cada chamada compila uma instrução. O `Up` ou o `Down` de uma migration retorna uma delas, ou um
array delas, que o Runner roda em ordem.

> `nullable` e `default` são **propriedades**, não métodos: você as atribui
> (`->default = true`, `->nullable = true`), não as encadeia. Para remover um default
> existente em `alter`, atribua `Defaults::None`. Detalhes em
> **[Definindo tabelas](/manual/ADI/Databases/SQL/Schema/Blueprint/overview/)**.

**O que isso produz?** Para o `create()` acima, o PostgreSQL recebe:

```sql
CREATE TABLE "users" ("id" BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL PRIMARY KEY, "email" VARCHAR(190) NOT NULL UNIQUE, "active" BOOLEAN NOT NULL DEFAULT TRUE, "created_at" TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP)
```

MySQL e SQLite recebem a sua própria grafia da mesma tabela — veja
**[Dialects](/manual/ADI/Databases/SQL/Schema/Dialects/overview/)**. Como descrever colunas (a parte
`$Table->add(...)`) está em **[Definindo tabelas](/manual/ADI/Databases/SQL/Schema/Blueprint/overview/)**.

## Criar uma tabela com seus índices

Um índice não faz parte da definição da tabela: crie-o ao lado dela, com `$Schema->index()`, na
mesma migration. O `Up` retorna as duas instruções num array — elas rodam em ordem e, no PostgreSQL
e no SQLite, dentro da transação da migration:

```php
use Bootgly\ADI\Databases\SQL\Schema\Auxiliaries\Keys;
use Bootgly\ADI\Databases\SQL\Schema\Auxiliaries\Types;
use Bootgly\ADI\Databases\SQL\Schema\Blueprint;
use Bootgly\ADI\Databases\SQL\Schema\Migrating;
use Bootgly\ADI\Databases\SQL\Schema\Migration;

return new Migration(
   Up: fn (Migrating $Schema) => [
      $Schema->create('posts', function (Blueprint $Table): void {
         $Table->add('id', Types::BigInteger)->generate()->constrain(Keys::Primary);
         $Table->add('author_id', Types::BigInteger);
         $Table->add('slug', Types::String)->limit(190);
         $Table->add('published_at', Types::Timestamp)->nullable = true;
      }),
      $Schema->index('posts', 'slug', unique: true),           // posts_slug_unique
      $Schema->index('posts', ['author_id', 'published_at']),  // posts_author_id_published_at_index
   ],
   Down: fn (Migrating $Schema) => $Schema->drop('posts')
);
```

Uma lista de colunas forma um índice composto, na ordem dada. Sem `name:`, o índice recebe o nome
da tabela, das colunas e `index` ou `unique` — veja [Nomes gerados](#nomes-gerados). Remover uma
tabela remove os índices dela, então o `Down` só remove a tabela.

> [!WARNING]
> Por enquanto, `$Table->index()` dentro da closure do `create()` não tem efeito: ele monta a
> descrição do índice e a descarta, então a tabela é criada sem o índice — e sem erro. Retorne o
> `$Schema->index()` ao lado do `create()`, como acima.

O `constrain(Keys::Unique)` de uma coluna também faz a engine manter um índice único, mas com um
nome que a engine escolhe — `users_email_key` no PostgreSQL, `email` no MySQL,
`sqlite_autoindex_users_1` no SQLite. Quando uma migration futura puder ter de removê-lo, prefira o
`index(..., unique: true)`, cujo nome você conhece.

### Indexar uma tabela que já existe

Numa migration posterior, o `index()` sozinho é a mudança, e o `unindex()` — que recebe o nome do
índice — a desfaz:

```php
return new Migration(
   Up: fn (Migrating $Schema) => $Schema->index('posts', ['author_id', 'slug']),
   Down: fn (Migrating $Schema) => $Schema->unindex('posts', 'posts_author_id_slug_index')
);
```

O `CREATE INDEX` é compilado sem `IF NOT EXISTS`, então criar um índice cujo nome já existe falha.

## Alterar uma tabela

O `alter()` compila um `ALTER TABLE` com tudo o que a closure pede: colunas novas (`add()`),
alteradas (`change()`), renomeadas (`rename()`), removidas (`remove()`) e chaves estrangeiras
(`reference()`). Quanto cabe num `alter()` depende da engine:

- O **PostgreSQL** junta as ações com vírgulas — exceto um rename de coluna, que vai num `alter()`
  só dele. Um rename ao lado de qualquer outra ação, inclusive de um segundo rename, lança
  `InvalidArgumentException: PostgreSQL renames a column in an ALTER TABLE of its own: give each rename its own alter(), with no other action beside it.`
- O **MySQL** junta todas as ações, inclusive renames.
- O **SQLite** aceita uma ação por `alter()`. Uma segunda lança
  `InvalidArgumentException: SQLite schema dialect lacks capability: MultiActionAlter.`

No PostgreSQL e no MySQL:

```php
use Bootgly\ADI\Databases\SQL\Schema\Auxiliaries\References;

$Schema->alter('users', function (Blueprint $Table): void {
   $Table->add('team_id', Types::BigInteger)->nullable = true;
   $Table->remove('legacy');
   $Table->reference('team_id', 'teams')
      ->delete(References::SetNull)
      ->update(References::Cascade);
});
// ALTER TABLE "users" ADD COLUMN "team_id" BIGINT, DROP COLUMN "legacy", ADD CONSTRAINT "users_team_id_teams_fk" FOREIGN KEY ("team_id") REFERENCES "teams" ("id") ON DELETE SET NULL ON UPDATE CASCADE
```

Uma migration que também precisa rodar no SQLite retorna um `alter()` por ação, num array — um
formato que toda engine aceita:

```php
return new Migration(
   Up: fn (Migrating $Schema) => [
      $Schema->alter('users', fn (Blueprint $Table) => $Table->rename('bio', 'profile')),
      $Schema->alter('users', fn (Blueprint $Table) => $Table->remove('legacy')),
   ],
   Down: fn (Migrating $Schema) => [
      $Schema->alter('users', function (Blueprint $Table): void {
         $Table->add('legacy', Types::Text)->nullable = true;
      }),
      $Schema->alter('users', fn (Blueprint $Table) => $Table->rename('profile', 'bio')),
   ]
);
```

O `Down` traz de volta a coluna `legacy`, não os dados dela. Que mudanças de coluna cada engine
aceita — tipo, default, nulidade — está na tabela de
**[Dialects](/manual/ADI/Databases/SQL/Schema/Dialects/overview/#o-que-cada-engine-consegue)**, e
como escrevê-las está em
**[Alterando uma tabela depois](/manual/ADI/Databases/SQL/Schema/Blueprint/overview/#alterando-uma-tabela-depois)**.

## Remover e rodar de novo

O `drop()` escreve `IF EXISTS`, a menos que você passe `exists: false`, em toda engine — então
remover uma tabela que já não existe dá certo. O `unindex()` e o `unconstrain()` recebem o mesmo
flag `exists`, também `true` por padrão, mas nem toda engine o respeita: o PostgreSQL respeita nos
dois e o SQLite no `unindex()`, o MySQL o ignora por enquanto, e o SQLite não consegue remover
constraint nenhuma. No PostgreSQL:

```php
$Schema->drop('users');                                   // DROP TABLE IF EXISTS "users"
$Schema->drop('users', exists: false);                    // DROP TABLE "users"
$Schema->unindex('users', 'users_email_index');           // DROP INDEX IF EXISTS "users_email_index"
$Schema->unconstrain('users', 'users_team_id_teams_fk');  // ALTER TABLE "users" DROP CONSTRAINT IF EXISTS "users_team_id_teams_fk"
```

As instruções de cada engine estão em
**[Removendo índices e constraints](/manual/ADI/Databases/SQL/Schema/Dialects/overview/#removendo-índices-e-constraints)**.

> [!WARNING]
> Por enquanto, o MySQL ignora o `exists` no `unindex()` e no `unconstrain()`, então remover um
> índice ou uma chave estrangeira que já não existe falha lá com
> `1091: Can't DROP '…'; check that column/key exists`. O MySQL roda uma migration sem transação:
> quando um `Down` falha assim, as instruções anteriores continuam aplicadas, a migration continua
> registrada como aplicada, e uma nova tentativa falha do mesmo jeito. Onde um `Down` puder remover
> a tabela inteira, faça isso — os índices e as chaves estrangeiras dela vão junto.

## Nomes gerados

Quando você não passa `name:`, o `index()` e o `reference()` de tabela dão nome ao que criam:

- um índice: `<tabela>_<colunas>_index`, ou `<tabela>_<colunas>_unique` com `unique: true` —
  `posts_author_id_published_at_index`;
- uma chave estrangeira: `<tabela>_<coluna>_<tabela referenciada>_fk` — `users_team_id_teams_fk`,
  com cada `.` de um nome qualificado por schema trocado por `_`.

Um nome gerado com mais de 63 bytes — o limite de identificador do PostgreSQL; o do MySQL é de 64
caracteres — é encurtado para os seus primeiros 54 bytes, um `_` e os 8 primeiros dígitos hex do
hash SHA-256 do nome inteiro. A mesma tabela com as mesmas colunas sempre dá o mesmo nome, então um
`unindex()` posterior pode repeti-lo:

```php
$Schema->index('subscription_invoices', ['billing_account_id', 'invoice_issued_at'], unique: true);
// CREATE UNIQUE INDEX "subscription_invoices_billing_account_id_invoice_issue_3301c710" ON "subscription_invoices" ("billing_account_id", "invoice_issued_at")

$Schema->unindex('subscription_invoices', 'subscription_invoices_billing_account_id_invoice_issue_3301c710');
```

Um `name:` que você passa é usado como está: o Bootgly não o encurta. O PostgreSQL então corta um
nome com mais de 63 bytes para 63, o MySQL recusa um com mais de 64 caracteres
(`1059: Identifier name '…' is too long`), e o SQLite aceita qualquer tamanho.

> [!WARNING]
> Por enquanto, o nome gerado de um índice numa tabela qualificada por schema mantém o ponto:
> `$Schema->index('audit.users', 'email')` dá ao índice o nome `audit.users_email_index`, que
> compila como `"audit"."users_email_index"`, e o PostgreSQL (`syntax error at or near "."`) e o
> MySQL (`1064`) recusam a instrução. Numa tabela qualificada por schema, passe `name:`.

## Usar fora de uma migration

Mudanças de schema pertencem às migrations, que o Runner registra e consegue desfazer. Quando uma
função de boot, um comando ou um script precisar de DDL mesmo assim, abra o banco como
**[Abra um banco](/manual/ADI/Databases/SQL/overview/#abra-um-banco)** mostra, pegue o Schema
Builder dele e rode o que ele compila:

```php
use Bootgly\ADI\Databases\SQL\Schema\Auxiliaries\Keys;
use Bootgly\ADI\Databases\SQL\Schema\Auxiliaries\Types;
use Bootgly\ADI\Databases\SQL\Schema\Blueprint;

$Schema = $Database->structure();

$Query = $Schema->create('settings', function (Blueprint $Table): void {
   $Table->add('key', Types::String)->limit(100)->constrain(Keys::Primary);
   $Table->add('value')->nullable = true;  // no type: Types::Text
}, exists: true);

$Database->await($Database->query($Query));
```

O `structure()` cria o Schema Builder da fachada na primeira chamada e devolve o mesmo depois. Com
`exists: true` a instrução é `CREATE TABLE IF NOT EXISTS`, então o script pode rodar de novo.

## Bom saber

- **Uma coluna sem tipo é `Types::Text`**: `$Table->add('value')` compila `"value" TEXT NOT NULL`.
- **Blueprints vazios são rejeitados.** Um `create()` sem coluna e sem chave estrangeira lança
  `InvalidArgumentException: CREATE TABLE requires at least one column or constraint.`, e um
  `alter()` sem ação lança `InvalidArgumentException: ALTER TABLE requires at least one schema action.`
- **Nomes são tipados.** Todo nome de tabela e de coluna — e o nome de índice ou de constraint que
  o `unindex()` e o `unconstrain()` recebem — aceita uma `string`, qualquer `Stringable` ou um
  backed enum, cujo `value` é usado; veja
  **[Dica: nomes tipados com enums](/manual/ADI/Databases/SQL/Schema/Blueprint/overview/#dica-nomes-tipados-com-enums)**.
  O `name:` que você passa ao `index()` ou ao `reference()` é uma `string` simples: um enum ali
  lança um `TypeError`.
- **Um ponto qualifica.** `'audit.users'` compila como `"audit"."users"`, um schema e uma tabela,
  então um nome não pode conter um ponto próprio.

## Referência

Pegue um Schema Builder de uma fachada de banco com `$Database->structure()` — veja a Referência de
**[Banco SQL](/manual/ADI/Databases/SQL/overview/#referência)** — ou crie um para um dialeto. As
closures de migration o recebem tipado como `Migrating`.

### Schema

`Bootgly\ADI\Databases\SQL\Schema`. Nas assinaturas, `QueryDialect` é
`Bootgly\ADI\Databases\SQL\Builder\Dialect` e `SchemaDialect` é
`Bootgly\ADI\Databases\SQL\Schema\Dialect`.

```php
__construct (null|QueryDialect|SchemaDialect $Dialect = null)
```

Cria um Schema Builder. Um dialeto de schema é usado como veio — o jeito de plugar um dialeto seu
(veja **[Escrevendo um dialeto](/manual/ADI/Databases/SQL/Schema/Dialects/overview/#escrevendo-um-dialeto)**).
Um dialeto do Query Builder é mapeado para o dialeto de schema da mesma engine, e `null` significa
PostgreSQL. Um dialeto do Query Builder sem par de schema lança
`InvalidArgumentException: Schema Builder dialect is not registered.`

```php
public private(set) SchemaDialect $Dialect
```

O dialeto de schema com que o builder compila. Leia-o para perguntar o que a engine suporta —
`$Schema->Dialect->check(Capabilities::AlterColumnUsing)` — ou se ela roda DDL numa transação,
`$Schema->Dialect->transactions` (veja
**[Dialects](/manual/ADI/Databases/SQL/Schema/Dialects/overview/#referência)**).

```php
create (BackedEnum|Stringable|string $Table, Closure $Build, bool $exists = false): Query
```

Compila um `CREATE TABLE`. O `$Build` recebe um `Blueprint` novo para `$Table`: adicione nele as
colunas e as chaves estrangeiras de tabela (veja
**[Definindo tabelas](/manual/ADI/Databases/SQL/Schema/Blueprint/overview/)**). `exists: true`
adiciona `IF NOT EXISTS`. Um blueprint sem coluna e sem chave estrangeira lança
`InvalidArgumentException: CREATE TABLE requires at least one column or constraint.` Índices
declarados no blueprint não são compilados — veja
[Criar uma tabela com seus índices](#criar-uma-tabela-com-seus-índices).

```php
alter (BackedEnum|Stringable|string $Table, Closure $Build): Query
```

Compila um `ALTER TABLE` com o que o `$Build` adiciona a um `Blueprint` novo: `ADD COLUMN` para cada
`add()`, as mudanças de coluna de cada `change()`, `RENAME COLUMN` para cada `rename()`,
`DROP COLUMN` para cada `remove()` e `ADD CONSTRAINT … FOREIGN KEY` para cada `reference()`, nessa
ordem. Um blueprint sem ação lança
`InvalidArgumentException: ALTER TABLE requires at least one schema action.` O PostgreSQL recusa um
rename ao lado de outra ação e o SQLite uma segunda ação (veja [Alterar uma tabela](#alterar-uma-tabela)),
e uma ação que falta à engine lança
`InvalidArgumentException: <Dialect> schema dialect lacks capability: <Capability>.`

```php
drop (BackedEnum|Stringable|string $Table, bool $exists = true): Query
```

Compila um `DROP TABLE`, com `IF EXISTS` a menos que `exists: false`, em toda engine.

```php
rename (BackedEnum|Stringable|string $From, BackedEnum|Stringable|string $To): Query
```

Compila o rename de uma tabela: `ALTER TABLE "users" RENAME TO "members"` no PostgreSQL e no
SQLite, ``RENAME TABLE `users` TO `members` `` no MySQL.

```php
index (BackedEnum|Stringable|string $Table, BackedEnum|Stringable|string|array $Columns, null|string $name = null, bool $unique = false): Query
```

Compila um `CREATE INDEX` — `CREATE UNIQUE INDEX` com `unique: true` — sobre uma coluna ou uma
lista de colunas, em ordem. Sem `$name`, o nome é gerado (veja [Nomes gerados](#nomes-gerados)).
Não há `IF NOT EXISTS`: um índice cujo nome já existe falha no servidor.

```php
unindex (BackedEnum|Stringable|string $Table, BackedEnum|Stringable|string $Name, bool $exists = true): Query
```

Compila um `DROP INDEX` para o índice `$Name`. O `$exists` adiciona `IF EXISTS` no PostgreSQL e no
SQLite; o MySQL o ignora por enquanto e compila `` DROP INDEX `name` ON `table` ``. O PostgreSQL
usa o schema de um `$Table` qualificado por schema: `unindex('audit.users', 'users_email_index')`
compila `DROP INDEX IF EXISTS "audit"."users_email_index"`. O SQLite não usa o `$Table`.

```php
unconstrain (BackedEnum|Stringable|string $Table, BackedEnum|Stringable|string $Name, bool $exists = true): Query
```

Compila a remoção da constraint `$Name`. O PostgreSQL compila `ALTER TABLE … DROP CONSTRAINT`,
com `IF EXISTS` a menos que `exists: false`, para qualquer constraint. O MySQL compila
`ALTER TABLE … DROP FOREIGN KEY`, que só remove chaves estrangeiras, e ignora o `$exists` por
enquanto. O SQLite lança
`InvalidArgumentException: SQLite schema dialect lacks capability: DropConstraint.`

### Migrating

`Bootgly\ADI\Databases\SQL\Schema\Migrating` é a interface com que as closures de migration tipam
o `$Schema`. Ela declara os sete métodos de compilação acima — `create`, `alter`, `drop`, `rename`,
`index`, `unindex` e `unconstrain` — com as mesmas assinaturas. O `Schema` a implementa, e o Runner
sempre passa às closures o `structure()` do banco dele.
